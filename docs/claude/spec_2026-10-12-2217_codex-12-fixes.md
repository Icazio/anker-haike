# Codex 20:25 复测 12 个非语言问题的修复方案

来源：`docs/planning/2026-10-12-2020_card-fact-retest/给Claude的修复清单.md`（Codex 20:25 轮，运行代码与 6f37156 指纹一致）。
取证方式：只读 Codex 复测库 `haike_eval_20261012_2020` 的 LangGraph checkpoint（事实、候选、synthesize 丢弃原因），对照 `data/official/qa.yaml` 原文与原图。
决策：T61 / T37 / T40 / T34 的方向由 Fable 5.1 裁定（用户授权）。语言问题不在本次范围。

## 原则

1. 客户可见的排障正文只用官方原文；系统只能加「框架句」（说明已知事实、资料覆盖边界、怎么反馈），不新增步骤、不新增承诺。
2. 资料不覆盖就如实说并转人工；不为了出卡而套用标题相近但主体不同的条目。
3. 先修事实层（客户原话 → 事实），再修决策层（候选适用性），最后修表达层（卡片框架句）。上游修好的，下游不再打补丁。

## 不做的与边界

- T48 裂纹是否进损坏 / 质保流程、T41 物流插队：仍待用户决定，不在 12 案范围。
- T30 / T42 / T48 的视觉改动只能靠真实模型复测验证；单测不调真实模型。
- T52 的修复依赖「one side」这类表述；其他对象混淆（盒子 vs 泵）仍由已有的充电关系规则处理。

## 验证

- 单测：每案新增回归（原始工单 + 同义 / 否定 / 对象互换对照），注明案例号；相关测试文件全跑；`make lint`。
- 真实复测：`make up` 重建后，用 Codex 的 HTTP 驱动方法（新会话、原文 + 原附件、操作卡模拟未解决、未知事实停止）跑 12 案主轮 + T27 / T30 / T40 / T52 各两次重复，按 Codex 的综合标准逐案对照；另跑全量 63 单主轮看有无回退。
- `scripts/ci-local.sh` 通过后再提交。

## 实施后勘误（2026-10-13）

按复测发现的问题追加，原方案不改：

- T30：提示词给可见判据后，deepseek 仍稳定把机器人写成基站（qwen-vl / glm-v 正确）。Fable 裁定不换主模型，改为错误码选路时首卡不回显读图（`graph.py`），读图仍进内部记录与安全检查。
- T37：主轮有时选 rv-0021 而不是 rv-0111，rv-0021 的「normal protective mechanism」同样不适用，一并覆写。
- T40：静默切换后 rv-0371 被计为「已走完一条指南」，rv-0073 首卡未解决即宣布排障完成；`replay_end` 把原文缺口计划排除在外。长邮件现象事实整段漏抽时补「客户原文兜底有效症状」（原文是愿望 / 评价时不兜底）。
- T41：模型把物流排为主诉求时补抽被跳过；补抽条件改为排障在主或次诉求中。整句 quote 让无关观察「覆盖」前提，前提比对只看 value 所在分句。
- T61：时机冲突候选丢弃后，0.25 置信度的候选去追问；低于换方案门槛（0.3）的候选不再追问。
- T13（回退）：模型判 request_human 却无原文引文时反问中文「要人工还是继续」；表单报故障时按排障处理。
- T27（波动）：首封消息里模型把已做检查写成 corrections，拦掉补抽；没有目标的更正不算更正，也不追问。
