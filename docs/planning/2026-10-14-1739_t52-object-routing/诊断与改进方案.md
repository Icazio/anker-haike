# T52为什么反复串到泵的排障

结论：与T48一样存在“资料存在不等于正确使用”的问题，但T52已证实的主要缺口在适用性判断和执行边界。系统保留了用户说的充电盒，也正确用充电盒检索，却仍批准泵不开机流程。继续补提示词或只新增一条知识不能保证解决。

本轮完成原始记录分析和当前代码的确定性探针，没有修改业务代码、调用真实模型重跑或发布。探针是重建候选输入后执行真实过滤及反馈函数，不能冒充新一次真实模型复现。

## 从原话到错误步骤

用户原话：My charging case will not charge therefore I cannot charge my pump motors. I am an exclusive pumper。

中文：充电盒自身充不进电，因此也没法给泵充电；我完全依赖吸乳。

| 环节 | 实际记录 | 判断 |
| --- | --- | --- |
| 理解与保存 | 两条事实分别保留subject=charging case、subject=pump motors；原话中的therefore也保留在引文中 | 不是完全没识别出盒子，也不是原话已丢失 |
| 检索 | search_query_en是charging case will not charge | 查询主语正确，不能简单归为意图提取全错 |
| 候选资料 | 同时召回盒给泵充电、泵不开机、充电时长等资料 | 型号相同与充电主题相近不等于能处理盒自身受电 |
| 选路 | qa_bp_0114，置信度0.7，理由是“充电盒不充电导致泵无法充电，计划包含检查充电盒指示灯和接触” | 用“步骤里提到盒子”替代“这个计划适合当前故障” |
| 自动选分支 | matched_section=Breast pump cannot be turned on；日志question_answered_from_facts | 用户没说泵无法开机，系统推断却进入了“事实已确认”的执行路径 |
| 操作 | 泵复位→看盒与泵指示灯→换盒→查泵盒接触→磁吸线→泵按钮是否到货损坏 | 第一条已偏离，随后持续沿错误计划推进 |

以上来自本机原始记录：`../2026-10-14-1648_official-63-readable/repeat/T52.json`及`state/repeat/T52.json`。最终状态不等于每个中间节点的完整输入输出，因此不据此断言某一次模型究竟漏读了哪段文字。

## 当前代码的三个缺口

**1．冲突拦截依赖选择方案的模型主动报错。**

`synthesize.py`已明确提示：盒自身不进电与盒给泵充电不同；A坏了导致B不能用，不应只处理B。但`filter_hypotheses`只有收到模型填写的`conflict`才走对象冲突拦截。模型说supported、引用有效证据、选择有效症状时，系统没有独立的部件和充电方向约束。

本轮探针从已保存rank重建候选，显式设置applicability=supported、conflict=None。当前代码保留qa_bp_0114，断言“盒自身受电故障不应放行泵不开机流程”失败。只增加object冲突字段后，同一候选被丢弃。输出保存为本机`probe-result.json`。

这证明过滤层缺少独立约束；并不声称重建的字段是原始模型响应原文，因为保存的rank不含原始applicability和conflict。

**2．分支名称合法，被当作分支事实成立。**

过滤检查matched_section是否属于计划的选项；`graph.py`随后把它写成source=fact的回答并跳过首问。它没有在该处要求一个能证明“泵无法开机”的用户事实引用。“确有这个选项”和“用户确有这个症状”是两回事。

现有FactCandidate已经有subject、quote、polarity，不能简单再加一个同名对象字段。需要把主诉对象、用户所述因果、当前诊断目标贯穿到选路和执行，并保留依据；用户说的因果只是用户陈述，不等于物理根因已证实。

**3．错误拦住后的追问，以及错误放行后的推进，都缺少针对性。**

冲突模板会问“是盒子本身，还是它与其他部件配合的问题”。用户原话已明确盒子自身充不进电，这个问题容易重复已知事实。应只追问仍未知、且能决定下一步的可观察信息。

`apply_feedback`收到not_solved后按next_on进入下一步。本轮探针以s2泵复位为起点，得到next_on:s3。正常排障需要这种推进，不能全面取消；但前提应是当前计划仍适合当前诊断目标。客户的“没解决”不能被解释成认可“泵坏了”。

## 推荐改法：明确目标，再批准动作

“诊断目标”指这轮究竟要查哪个对象的哪项能力。例如T52是“充电盒从外部电源受电失败”，不是泛泛的“充电问题”。

建议第一阶段做一个贯穿理解、选路、分支和步骤的最小闭环：

1. **区分对象与充电方向。** 同型号下分清外部电源给盒充电、盒给泵充电、线直接给泵充电、泵能否开机。沿用现有事实与引文，补充规范化对象、关系和当前目标；不靠中英文关键词黑名单。未知值允许保留未知，客户纠正后更新目标并使旧适用性结论失效。
2. **给知识的可执行部分标适用条件。** 用人工核对的覆盖文件标注适用故障、必要条件、分支和步骤目标；不手改生成qa.yaml。不只标整篇文章，因为一篇可能同时讲盒和泵。模型负责找候选，服务端根据已核实元数据检查适用关系；元数据缺失时不能默认为适用。
3. **把分支选择与用户事实绑定。** 自动进入“泵不开机”分支必须指出相关用户事实及依据；仅有“泵无法通过盒充电”不成立。引文存在只是必要条件，还要符合规范化的对象与症状关系。模型推断保留为推断，不能直接写成用户确认事实。
4. **每次发步骤前检查目标和用途。** 核对其是在诊断主诉、进行有依据的关联测试，还是临时替代办法。不能简单禁止操作其他部件：换线等关联测试可能必要，给泵临时供电也可能有帮助，但都需有适用证据、解释目的；临时能用不代表盒已修好。
5. **缺知识时明确缺口。** 如果没有盒自身受电故障的适用资料，不得选泵流程凑步骤。可问一个确实缺失的观察信息；仍无可用依据则说明知识不足并提供合适服务路径。后续沿方案1补充经过核对的资料。

最先落地的范围可以仅覆盖吸奶器充电相关知识，但机制应通用。需要同时覆盖入口批准和发卡前复核，否则只补其中一层仍可能从另一条路径进入错误流程。

## 为什么不优先换模型或再加一个审核agent

更强模型或第二次语义审查可能降低漏判概率，但仍可能重复同一误解，且增加成本与延迟；本轮未做模型对比，不能宣称换模型无效或必然有效。先让程序能表达并检查“正在查什么、这一步为什么适用”，再考虑对未知范围增加模型审查。

同样不建议只提高检索数量、调高置信度门槛或给bp-0114加一条排除T52的特例。当前错误候选已有0.7置信度；真正缺的是适用性的证据和约束。

## 验收怎么避免再次出现“单测通过，实测仍错”

已有T52相关测试会构造正确的object冲突来验证拦截。这能证明“报告冲突后会拦”，不能证明“模型漏报时仍会拦”。新增回归必须包含故意错误的高置信度候选，不把预期结论预先塞给模拟模型。

| 测试场景 | 必须满足 |
| --- | --- |
| 盒自身不充电，所以泵没法充 | 主目标保持盒受电，不自动进入泵不开机分支 |
| 模型以0.95说泵方案适用且不报冲突 | 服务端仍拦不适用计划或转入明确的适用性待确认状态 |
| 客户明确盒能充电，只有泵在盒内不充 | 允许合适的盒给泵充电流程，防止一刀切误拦 |
| 直接给泵充电正常，盒受电仍异常 | 保留盒故障主线，不把替代办法当作解决 |
| 客户只说“充不了电” | 先确认哪个对象、哪条充电路径，不猜 |
| 客户说“不是盒，是左泵” | 更新诊断目标，旧候选与旧卡片适用性需重新确认 |
| 连续反馈“没解决” | 不凭反馈创造新症状；下一步仍有目标和用途依据 |
| 一个消息同时提盒和泵、带否定和因果 | 分清主诉、后果、已排除现象；覆盖中英文改写 |

改完后应以真实模型复跑T52，并联合T44、T48、T51、T53、T54、T55检查边界；每案保留目标、候选拒绝原因、分支依据和发出步骤，而不是只看最终回答是否有礼貌。

## 问题分类

主类：系统选路与执行约束。次类：agent适用性判断不稳定、知识缺少部件/关系层的适用标注、用户所述因果未成为可执行约束。

不是本次已证实的主因：图片识别、官方没有说明、检索完全没执行。官方资料是否充分覆盖“盒自身受电”的具体排障步骤，需要另行逐条核对；本轮不编造充电参数、按钮或复位方法。
