# 测试方法与失败记录

## 怎样测试

运行入口为 `make t52-regression ARM=记录目录 IDS=案例列表`。入口调用 `app.evaluation.charging_scope`，使用当前源码的 HTTP 会话链路，真实模型、真实知识库；订单与售后服务用内存实现。保修判定按本轮运行日 2026-10-15 和测试订单，不能把结果当成真实客户的最新保修权益。

原始工单保持原文及原始附件，不把工单之外的型号偷偷补进首条消息。仅遇到产品选择卡时按原工单选择；带后缀场景的改写和第二轮文本在脚本中明确保存。操作卡统一反馈未解决，问句停住，不能从合成反馈推断设备真的坏在哪里。

每轮 JSON 保存输入、HTTP 事件、完整状态和快照，包括事实引用、关系、检索、模型轨迹、方案与卡片。文件位于 `reports/eval/t52-production/`，按项目约定只留本机、被 `.gitignore` 忽略；中文结论文档可以正常入库。

| semantic-check | 加强“尝试充电不等于充电失败”边界后的 6 场、29 轮：T53 两次、T51、T52、盒输出、磁吸直充 |

语义补测期间也补全了磁吸直充方案的审核标注。`verified` 进程启动早于最后这两项修订，不能把它冒充最终提示词的整批回归；最后直接相关场景由 `semantic-check` 补测。评测器最后的轮数修订只改变测试驱动，不改生产路径。

## 错误怎样处置

- T52 原始旧记录的错路已存在；此次修改前未稳定重现，所以另写强制错选测试：假模型给错误泵方案 0.99 置信度，程序必须拒绝，HTTP 链路不得发卡。
- 第一版真实模型超时，最小探针也要 7646 ms。先排除错误候选，再按实测扩大时限，不把超时记成对象判断成功。
- 容量单测先因旧阈值失败，曾尝试按品类拆 schema；按用户要求撤回这种额外复杂度，保持统一结构。新增续航和左右侧后重新实测，最终阈值保留约 10% 余量。
- 更长运行时限使回执和执行器不一致的单测失败，修成共享时限来源后通过。
- 增加官方范围标注时，两个原文短引先写得不准确；在真实新进程启动前改为官方实际标题文字，并由来源校验测试确认。
- T51 从运行中断误走充电不足，增加 pump_runtime 后重测恢复。
- T53 从“充电后不开机”抽出错误关系，扩大字段定义和正反例；最后原文两次都为 pump_power。
- 评测器曾在第 7 轮记录后再发送一次未保存反馈；已修复，T54 另补完整收尾，不将早期七轮当整单终态。
- T44 先排障要求未被执行、T53 纠正后结案文案不足，保留为未解决，不隐藏。
