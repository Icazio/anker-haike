# qwen3.8-flash 本次不替换：真实请求对照记录

验证日期：2026-10-15。结论只针对本机、当前接入配置与本次采样，不代表模型长期或所有地区的表现。

用户要求是“没问题的话就改”。本次未满足条件：新版在 13 个真实理解案例中 2 个超时，另有 1 个摘要整理超时。项目模型配置保持原样，qwen-flash 仍对应 qwen3.7-flash；备用顺序也未调整。

## 1. 一眼看懂结果

“返回成功”仅指接口返回并通过结构校验，不等于理解正确。理解耗时是 interpret_turn 整次调用墙钟耗时，包含失败等待；不是整单处理时长。

| 指标 | qwen3.7-flash | qwen3.8-flash |
|---|---:|---:|
| 真实理解案例返回成功 | 13 / 13 | 11 / 13 |
| 理解案例超时 | 0 | 2（T50、T53） |
| 13 例理解耗时中位数，含超时 | 5.358 秒 | 9.717 秒 |
| 7 秒内完成理解的样本数 | 10 / 13 | 3 / 13 |
| 摘要整理接口成功 | 3 / 3 | 2 / 3 |
| 搜索词改写接口成功 | 3 / 3 | 3 / 3 |
| 知识条目相关性判断接口成功 | 3 / 3 | 3 / 3 |
| 全部 22 项任务接口成功 | 22 / 22 | 19 / 22 |

新版理解耗时中位数约为旧版 1.81 倍。部分语义判断有改善，但速度与超时表现不适合直接作为当前快速备用模型。

## 2. 测试如何进行

1. 保存任务开始时的 models.yaml 快照。用临时配置仅把 qwen-flash 的模型 ID 改成 qwen3.8-flash。项目配置未改。
2. 保留 json_object 结构化输出、enable_thinking=false、15 秒模型超时及现有提示词。最小真实探针成功，耗时 4.758 秒；该探针只能证明接口能调用。
3. 从 63 个官方工单中抽取 13 个有代表性的真实原文，覆盖物流、多意图、多语言、否定表达、安全、充电因果、维修/更换、时间和配件。调用当前 interpret_turn，不使用旧版 intake 测试适配器。
4. 两版本分别顺序执行同组样本，两个进程同期运行；两版之间并非随机交叉测试，网络与服务负载可能影响比较。每项只执行一次，不用重试掩盖失败。
5. 为隔离模型差异，测试路由固定为单个 qwen-flash，关闭同模型和限流重试。因此本次不是完整多模型故障切换测试。
6. 对摘要整理、搜索词改写、知识相关性判断各补充 3 个现有样本，每个版本共 22 项任务，总计 44 项，另有 1 次最小探针。
7. 手工核对原文与结构化输出。知识相关性测试使用固定候选条目，未访问真实知识库；未运行图片识别，也未验证订单操作或官方售后承诺。

摘要整理虽然从评测适配器传入 20 秒，实际函数将预算限制在 3 秒；本次确实测到了这个生产限制。搜索词改写及知识判断使用评测适配器 20 秒预算，不能据此宣称所有生产时限都已通过。

最小探针命令：`MODELS_CONFIG_PATH=/tmp/haike-qwen38.yaml make model-probe TASK=intake ALIAS=qwen-flash`。
批量对照通过临时 Makefile 调用 `uv run --env-file ../.env python`。脚本副本保存在本机的 [验证脚本.txt](验证脚本.txt)，候选与原配置均有本机快照。临时执行文件完成后删除。

### T3

用户意思：请告知何时寄出我购买的 X10，订单号 Anker003。

我的判断：新版正确聚焦发货查询；旧版额外识别为查询订单号。新版改善，但订单关联是否完成需要整链验证。

### T9

用户意思：7 日买的吸尘器何时发货？目前只收到滤网。如果还没寄出，请先不要寄，我们先谈其他产品。对延迟却没人联系我感到不满。

我的判断：两版均保留物流与暂停发货意图；新版保留“只收到滤网”事实。没有实际暂停订单，订单操作仍属于系统权限边界。

### T20

用户意思：荷兰语：X10 无法确定位置，任务终止，机器人返回基站。工单带图片链接，本次仅测文字理解。

我的判断：两版均识别定位失败、任务结束及返回基站。未处理图片，不能据此判断视觉能力。

### T41

用户意思：第二次出现烘干失败提示。注水仍有故障，所以没有运行拖地，也不需要烘干；为何出现错误？替换插头和更换说明何时到？

我的判断：两版均保留故障与物流双意图，未把“没运行拖地”当作已执行。新版将注水故障写成观察而非症状，最终分流影响未测。

### T43

用户意思：西班牙语：X10 机器人处于离线状态。

我的判断：两版均识别设备离线。新版未给诊断请求原句，但主意图仍为报障；是否影响后续流程未测。

### T44

用户意思：充电盒的一个针脚卡住或损坏，导致一侧泵无法充电。一直保持干燥清洁，排查无效；询问保修或更换。原文含不清楚的“trouble shorted”，不能直接确定做过电气短接。

我的判断：两版均识别更换、保修及针脚故障；新版补出了盒到泵的充电关系，但把含糊的“trouble shorted”写成已尝试短接，存在事实过度推断。

### T45

用户意思：S1 Pro 吸奶器不能充电，加热部件烫伤了我，现在看起来变色。附购买证明、序列号、国家等资料。

我的判断：两版均识别烫伤安全风险。新版把空白字段“Order No:”误解为查询订单号；旧版额外加保修意图。安全识别通过不等于意图完全正确。

### T50

用户意思：我有 S1 吸奶器，左边那只确实能工作。原文是 does work，不能擅自改成不工作。

我的判断：新版 15 秒超时，无法评判其语义结果；旧版虽返回，却将明确“能工作”标为不确定症状。不能把旧版返回成功记为业务正确。

### T52

用户意思：充电盒本身充不进电，因此无法给泵电机充电；我完全依赖吸奶器。

我的判断：两版均区分充电盒充电故障与泵充不进电的后果。新版将泵侧写成 both，原文没有明确左右两侧，存在过度细化。

### T53

用户意思：一侧泵停止工作，反复充电仍无法开机。买了 24 个月，但故障发生在前 12 个月，当时不知道可以申请售后。希望更换，或者帮助修好。

我的判断：新版 15 秒超时。旧版返回更换意图，但漏掉“或者修好”的诊断诉求，还把提供的订单资料当成查询请求。

### T56

用户意思：为什么每次需要 SoloCam S340 时它都离线？才接上一周。你们的保修就这样？用户非常生气。

### T61

用户意思：Omni C20 不按设定时间清扫，会提前两小时启动，App 也不记录清扫。

### T63

## 5. 失败为什么发生，有没有兜底

这里把“备用模型接手”和“失败后给出保底处理”分开说明。

T50：qwen3.8-flash → 15.006 秒仍未完成 → TimeoutError → 理解模块返回 degraded（降级），主意图 unknown（未知），提示暂时无法完成理解。T53 同样在 15.007 秒超时。可确定的是超过本系统截止时间；日志没有服务商排队或推理内部耗时，不能断言是服务商拥堵，也没有证据指向鉴权、模型不存在或结构格式错误。

本次为单模型对照，故意不放其他候选模型，所以不能用这两例推断线上没有配置备用模型。降级处理已经执行，但只是保留输入并提示重试/澄清，没有完成原任务。

摘要 spaces：模型尝试在 3.000 秒被取消 → polish_summary 返回原摘要。兜底有效，用户事实没有因润色失败而丢失。

当前完整理解链总预算 22 秒，首选 deepseek-pro 上限 15 秒。首选耗尽时只剩约 7 秒；本轮新版只有 3 / 13 在 7 秒内完成。因此只把它挪到第二也不能保证备用模型来得及回答。这是基于本次耗时的预算判断，并非已经实测完整链的成功率。
