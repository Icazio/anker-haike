# 方案复评

## 用户确认

- 云端只迁知识库和业务参考数据，历史会话和管理记录留在本机。
- 并发预期先回复 5–20 人，随后更正为 1–5 人，以后者为准。
- 用户询问是否需要 Nginx 等重组件。

## 设计调整

- 按 1–5 人试用设计，复用并升级现有 EC2，目标 t3.medium（2 vCPU / 4 GiB）、60 GiB 加密 gp3；最终由 5 人并发验收决定是否加内存。
- 复用当前宿主机 Caddy，不增加 Nginx、负载均衡器、Kubernetes、NAT Gateway 或第二台长期运行的 EC2。
- 升级需一次计划停机，EIP 与 Caddy 证书存储保留。完成升级后原隧道可继续服务，云端应用在独立回环端口准备，验收通过再切代理。
- 生产业务库从迁移和参考数据构建，禁止直接恢复本机 haike 全库。WeKnora 只迁知识内容及必要元数据，需排除其聊天/消息历史。
- Nginx 不是主要资源成本；数据库、知识服务及文档解析服务才是容量关注点。为保持能力，本次保留现有核心依赖。
- Langfuse 当前未启用，首期不增加该可选组件；现有管理台保留。
- 进一步核对发现 WeKnora 本身也有历史聊天；因此推荐两库都干净初始化，知识内容从冻结的官方 Q&A 重建，并比对是否存在额外手工知识。此路径避免复制历史、原数据库角色口令和加密模型配置；不需要保留旧 AES key，云端生成新值并重新登记模型。
