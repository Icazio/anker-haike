# 发现

- 会话页请求会话列表 limit=30，并读取全部案件队列。
- 工作台请求全部案件队列和会话事实 limit=100。
- Caddy 使用独立管理员基础认证，经云端回环端口 15173 转发到本机 Vite 5173，再代理 API 到 8000。
- 修复前代理没有显式配置响应压缩。
- 本轮开始时其他会话已修改 .gitignore 并生成若干评测文档，不触碰这些已有改动。
- 首次计时：会话列表 limit30 本机 14.7 ms / 公网 0.697 s；limit100 本机 14.0 ms / 公网 0.997 s。
- 全案件队列 176034 字节，本机 Vite 21.3 ms / 公网 6.078 s；公网首字节 0.351 s，随后主要等待传输。
- 队列最小复现再次测得本机 42.5 ms / 公网 4.246 s，触发 2 秒耗时门槛失败，问题可复现。
- 排序假设：SSH 传输缓慢；公网未压缩响应下载缓慢；开发模块加载放大页面等待。数据库查询当前只有几十毫秒，不能把主因归到数据库。
- 云端回环获取相同队列：首字节 0.178 s，总计 0.182 s；SSH 接收足够快，云端 CPU 100% idle，无 swap。
- 慢点位于 AWS 到当前访问网络的下载，增加 EC2 配置不能解释或解决该段传输问题。
- Caddy 支持 zstd/gzip 和按响应 Content-Type 限定压缩；本轮只压缩 JSON、HTML、JS、CSS、SVG，text/event-stream 继续原样透传。
  来源：https://caddyserver.com/docs/caddyfile/directives/encode
- 会话页独立加载列表和案件状态，工作台也同时加载队列与会话事实；它们都需要慢的队列请求，额外串行请求不是本轮已证实的主因。
- 已部署按响应 MIME 类型匹配的 zstd/gzip 压缩，不修改前后端、数据库、SSH 隧道和访问角色。队列 gzip 传输体积从 176034 降到 21685 字节，减少约 88%。
- 修复后的同一公网队列请求测得 0.557 / 0.390 / 0.740 秒；会话 limit30 为 0.337 秒、limit100 为 0.952 秒。全量基线的三个数据请求都低于原 2 秒门槛。
- 云端 Caddy 配置验证、重载及文件一致性检查通过。公网 viewer 首页/health 为 200，管理 API 为 401；admin 页面、会话、队列和共享 JS 为 200；TLS 校验结果均为 0。
- 6 项隔离代理回归检查通过，包括压缩后 JSON 数据相同、传输体积减少、事件流不压缩及原有身份边界；没有调用模型或知识库。
- 以上为接口测量，不代表完整浏览器首次加载时长。公网网络仍有波动，当前开发页面的模块请求与本机运行依赖仍存在。
